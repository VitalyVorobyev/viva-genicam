# viva-genicam 0.8

Releases in the 0.8 series, newest first. The [changelog index](../CHANGELOG.md)
lists every series.

## [0.8.0] - 2026-10-10

A breaking release. Read these before upgrading:
- **USB3 Vision was rebuilt to the standards**, from USB discovery up. Before
  this release no layer matched GenCP 1.2, a vendor's own XML, aravis or
  Wireshark, so it could not have worked with a real camera. It has still not
  been run on one: if you have a USB3 Vision camera, `viva-camctl report --usb
  0` is the most useful thing you can send. The `viva-u3v` API changed with it.
- **`TimeSync::to_host_time` and `Camera::map_dev_ts` return `Option`.** A
  frame's `ts_host` is `None` until `time_calibrate` has fitted the clocks.
  Calibration now fits real samples; before, it reported success while mapping
  every timestamp to its own start.
- **`<ImposedAccessMode>` is enforced.** A feature a camera declares read-only,
  such as FLIR's `SensorWidth`, now refuses writes.
- **The Python package needs Python 3.10 or later.**

Viva Studio ships as unsigned desktop bundles on this release for the first
time; see the user guide's Viva Studio chapter.

### Added

- `GigeDevice::set_control_timeout` / `control_timeout` configure the GVCP ACK
  timeout per attempt — register and memory access, control privilege and
  packet resend — retaining the 500 ms default. Low-level users can opt into
  probes during ACK waits with `set_inflight_keepalive_period`; the high-level
  GigE transport configures them from the device heartbeat window.
- `NodeMap::feature_state` and `Camera::feature_state` read everything a
  viewer needs about a feature in one call: its typed value, what it permits
  now, whether it is implemented and available, its range, the enumeration
  entries the device accepts and its unit (`FeatureState`, `FeatureValue`,
  `ValueRange`). `viva-service`, `viva-service-u3v` and Viva Studio each built
  this snapshot themselves, and Studio's copy had fallen behind (backlog
  ST-26). `viva-zenoh-api`'s new `genapi` feature converts it to the wire
  `FeatureState`.
- `NodeMap::invalidated_by` names the features a write can change: everything
  that depends, directly or transitively, on the written node or a node it
  writes through — selected features, converters over the same register,
  `<pMin>`/`<pMax>`, predicates and `<pInvalidator>`s. In the vendor corpus the
  median writable feature invalidates 3 others, the 90th percentile 72, and
  `PixelFormat` up to 539, so a viewer should re-read the ones it shows rather
  than all of them (backlog ST-30).

- `NodeOpResponse` carries `invalidated`: after a successful write or execute,
  `viva-service` and `viva-service-u3v` name the features it may have changed
  (`DeviceOps::invalidated_by`, from `NodeMap::invalidated_by`), so a client
  can re-read the ones it shows. `NodeOpResponse::ok()`/`err()` construct it.
- `viva-zenoh-api`'s `ts` feature derives `ts_rs::TS` on the payloads a UI
  receives (`FeatureState`, `NumericRange`, `CommandResult`,
  `AcquisitionStatus`, `ImageMeta`, `PixelFormat`), so a TypeScript client can
  generate its types from them. Off by default.
- `AcquisitionControlRequest` carries an optional `packet_size` for `Start`,
  which `viva-service` uses as the GVSP packet size ceiling instead of
  negotiating one; `AcquisitionControlRequest::new` builds a request without
  it. `DeviceHandle::build_stream` takes the same option.
- `keys::node_state_wildcard` subscribes to every `nodes/{name}/state`
  publication of a device.
- `viva_service::serve::serve_device` starts the task set the service runs for
  one camera, and `publish_announce` announces it. The binary and the tests
  share them; the service's own end-to-end test used to carry a copy that
  lacked the two feature-state queryables.
- `viva_genicam::report` writes the plain-text diagnostic report
  (`build_report`, `ReportRequest`, `ReportTarget`) that `viva-camctl report`
  writes, so other tools can produce the same file; the CLI is now a thin
  wrapper over it.
- The report covers USB3 Vision (backlog DX-06). It lists the USB3 Vision
  devices on the host, and `ReportTarget::Open` (`OpenCamera`) describes a
  camera the caller already holds — a USB device admits one owner, so the
  report cannot open it a second time the way it opens a GigE control
  channel. `viva-camctl report --usb N` reports on the Nth USB3 Vision camera,
  and `viva-service-u3v` answers `report` queries too
  (`viva_service::report::serve`).
- `viva-service` answers `genicam/devices/{id}/report` (`keys::report`,
  `DeviceReportRequest`, `DeviceReportResponse`) with that report on its
  camera, written on the host the camera is attached to (backlog ST-41).
- `gige::DeviceInfo::local_ip` is the host address a Discovery ACK arrived
  at. A broadcast meant for one camera, such as `force_ip`, has to leave from
  it (`Iface::from_ipv4`): sent from an unbound socket it leaves through an
  interface the OS picks, usually the default route's, which on a direct
  camera link is the wrong one. An address rather than an interface name, as
  first merged, because a NIC can carry several (Codex review of #177).
- Python: `Camera.skipped()` lists the declarations in the camera's XML that
  could not become features, as `SkippedNode`s with the element, name and
  reason, so a missing feature can be told apart from one the camera lacks
  (backlog DX-05).

### Changed

- `TimeSync::to_host_time` and `Camera::map_dev_ts` return
  `Option<SystemTime>`: `None` before a mapping exists (DOC-11).
- The Python package needs Python 3.10 or later (`abi3-py310`); 3.9 has been
  past end of life since October 2025, and GitHub's Ubuntu 26.04 runners no
  longer offer it, so it could not stay tested. Wheels are tested on 3.10 and
  3.14.
- USB3 Vision API, reshaped with the TC-27 fix: `ControlChannel` has no
  `read_register`/`write_register` (GenCP has no such commands) and gains
  `set_max_transfer`; `U3vStream::new` takes a `StreamLayout`; `Leader` gains
  `block_id` and `Trailer::status` is a `u16`; `Sbrm` gains
  `u3vcp_capability`; `Sirm` holds the device's half only, with `alignment()`
  and `configure(&StreamLayout)`; `ManifestEntry::read_first` is
  `read_device_xml`; `U3vDevice::open_stream`'s argument is a fallback for a
  device whose SIRM leaves the payload size at 0. `viva-gencp` gains GenCP's
  `command_id` and `ccd_flags`, and `OpCode` is documented as GVCP's.
- `viva-service`'s `acquisition/status` reports the stream's dropped frames
  (`StreamStats::drops`: frames abandoned incomplete or discarded because the
  service fell behind); `dropped` was always 0.
- `NodeMap::command_targets` returns `&HashSet<String>`, computed once when
  the map is built, instead of a fresh set on every call.
- `viva_service::device::build_feature_state` is gone; use
  `NodeMap::feature_state` with `viva_zenoh_api::FeatureState::from`.
  `camera_feature_state` no longer takes the command targets.

### Fixed

- An `<ImposedAccessMode>` binds every path to a node, not only the plain
  getters and setters (Codex review of #186): an imposed `WO` makes a feature
  write-only for feature state and the service's snapshots, an imposed `RO`
  stops a command from executing, a converter or SwissKnife refuses a read its
  ceiling forbids — directly or as a formula variable — and Studio shows the
  access the whole `<pValue>` chain allows rather than the first node's, `NA`
  when it allows nothing (Codex reviews of #186 and #187).
- `viva-service` stops serving and announcing a camera that a successful
  discovery pass no longer finds, including when it finds none: an empty pass
  was treated as a failed one, so an unplugged only camera was announced
  forever. And a device time maps to host time only once a fit of the samples
  has succeeded, not as soon as two samples exist (Codex review of #185).
- `Camera::time_calibrate` fits real samples. It read the latched timestamp
  through the feature cache, which nothing invalidated unless the camera's
  XML links the latch to the value, so every sample after the first repeated
  it, no fit was possible — and calibration reported success on default
  coefficients that mapped every timestamp to when calibration began. Each
  sample is now read fresh: `NodeMap::invalidate` forgets the cached value of
  a node and of everything behind its `<pValue>` — where a timestamp's
  reading is held in all 30 corpus cameras that have one (Codex review of
  #187). The fake GigE camera now declares its timestamp the same way. Found
  once a fit had to succeed.
- A USB3 Vision block whose trailer reports an error (the status's severity
  bit) is dropped and counted by `U3vFrameStream::dropped`, which Studio's
  dropped-frame count now includes, rather than handed on as an image; and a
  stream dropped while another thread holds the device still clears
  StreamEnable once it is free (Codex review of #184).
- **USB3 Vision now speaks the protocol the standards describe** (backlog
  TC-27). It could not have worked with a real camera: no layer matched what
  GenCP 1.2, a Grasshopper3's own XML, aravis and Wireshark agree on, and the
  fake camera had been written to the same misreading, so every test passed.
  No USB3 Vision camera has been reported either way. What changed:
  - Discovery matched interface *subclass* 0, 1 and 2; USB3 Vision interfaces
    are subclass `0x05` and differ by *protocol*. It found no camera.
  - Commands used GVCP's opcodes (`0x0084` …) and acknowledge flag (bit 0)
    with a big-endian address. GenCP's are READMEM `0x0800` and WRITEMEM
    `0x0802` with RequestAck at bit 14, every field little-endian, and an
    acknowledge carries the same `U3VC` prefix as a command; the decoder
    expected a prefix that spells `A3VC`. Request ids no longer start at, or
    wrap to, 0, which GenCP forbids for a write.
  - The ABRM was read at offsets of our own (the SBRM address at `0x230`
    instead of `0x1D8`) and big-endian, as were the SBRM, whose SIRM address
    was at +0x10 instead of +0x20, and the manifest.
  - The stream configuration wrote the payload, leader and trailer sizes to
    the SIRM's read-only *required* sizes, and never set the transfer layout
    a camera streams by (Codex review of #181); a stream now reads the
    required sizes, writes the layout, and reads each transfer at its size.
  - Stopping a stream never cleared StreamEnable (Codex review of #181);
    `U3vFrameStream` now does once its reader has stopped, and when dropped.
  - The stream leader and trailer were read without their 8-byte block id,
    so every field after it was misplaced.
  - The control timeout follows the camera's Maximum Device Response Time, a
    pending acknowledge extends the wait instead of sleeping it out, and a
    late answer to an earlier command is skipped.
  `viva-fake-u3v` is rebuilt from those sources with constants of its own; it
  refuses what a device refuses and streams only after StreamEnable and
  AcquisitionStart. `viva-camctl report --usb N`, Studio and
  `viva-service-u3v` add the camera's bootstrap registers, decoded and raw, to
  the report, and `report --usb` still describes a camera whose XML cannot be
  read.
- A frame's host time is a device time mapped to the host, or nothing
  (backlog DOC-11). `TimeSync::to_host_time` returned `SystemTime::now()`
  until two samples gave it a mapping, and the Python bindings never
  calibrated, so every Python GigE frame's `ts_host` was the wall-clock time it
  was handed over, passed off as its device time; `viva-camctl stream` did the
  same. It now returns `None` until calibrated, `Camera::map_dev_ts` likewise,
  and Python gains `Camera.time_calibrate()`.
- Viva Studio no longer drops cameras the GigE service is serving (backlog
  SVC-01). The service announced a camera only from its discovery loop, every
  discovery timeout plus discovery interval (about 7 s), while Studio forgets a
  camera unannounced for 6 s. A task of its own now re-announces each served
  camera every 2 s; `viva_zenoh_api::ANNOUNCE_INTERVAL` and `ANNOUNCE_EXPIRY`
  hold the contract, which `viva-service-u3v` (5 s until now) and Studio share.
- `viva-service --help` and its logs say `viva-service`, not
  `genicam-service` (backlog SVC-05), and it has a `--version`.
- `<ImposedAccessMode>` is honoured (backlog GA-23). The parser skipped it, so
  a feature a camera declares read-only over a writable register was
  reported, and written, as `RW` — FLIR's `SensorWidth` among them. It caps
  the access along the `<pValue>` chain as the declared modes do: `RO` removes
  writing, `WO` reading, `RW` nothing; reads and writes the ceiling forbids are
  refused. The corpus has 1 421 `RO` and 199 `WO` ceilings in 31 of its 38
  documents. `NodeMeta` gains `imposed_access`.
- An `<AccessMode>` value the parser does not recognise reads as `RO`, not
  `RW` (backlog GA-26): a register whose access we cannot read is not written.
- `viva-service-u3v` streams as the library does (backlog SVC-03, SVC-06). It
  built its own `U3vStream`, which skipped the SIRM — the streaming registers
  — and sized a packed format's frames at one byte a pixel, and read in a
  loop that slept to hold ~30 frames a second. It now opens a
  `U3vFrameStream` through `U3vStreamBuilder` and publishes every frame.
  `U3vDeviceHandle::new` takes the camera, its XML and its id only.
- `U3vStreamBuilder` returns a `PayloadSize` read that fails for any reason
  but a missing feature, rather than falling back to a computed size that
  misses the camera's padding or chunk data (Codex review of #180).
- A USB3 Vision stream of a packed format is sized right. `U3vStreamBuilder`
  sized frames as width × height × one byte when the format has no
  whole-byte pixel (`Mono12Packed`), and the reader then took the rest of the
  image for the trailer and failed; it now uses the camera's `PayloadSize`,
  and refuses rather than guesses when there is none (Codex review of #179).
- A USB3 Vision stream survives a wait for its next frame. A read timeout —
  five seconds without a frame, as in trigger mode — ended the stream in
  `U3vFrameStream` and in `viva-service-u3v`; they now poll with
  `U3vStream::next_frame_within`, which returns `None` for a stream that is
  waiting, and `RusbTransfer` reports a timeout as `U3vError::Timeout` rather
  than a generic USB error. `U3vFrameStream::shutdown` stops the reader and
  waits for it, so the endpoint is free for the next stream (Codex review of
  #179).
- GigE control heartbeats continue during long register/memory ACK waits,
  including `PENDING_ACK` extensions, while `GigeRegisterIo` holds the device
  mutex. The socket owner sends CCP reads with separate request IDs and drains
  their delayed or duplicate replies without extending the original deadline
  or repeating the active operation. Memory-only sessions use READMEM probes;
  packet resend waits also filter unrelated ACKs.
- Cancel and drain control-channel keepalive I/O when `GigeRegisterIo` is
  dropped, preventing timer registration from racing runtime shutdown.
- Stale acknowledgements can no longer stretch a GVCP attempt (TC-18). Each
  one used to restart the 500 ms receive timeout, so a trickle of them could
  hold one attempt for up to 4 × 500 ms; they are now drained against the
  attempt's fixed deadline. The count-based mismatch handling this replaces is
  removed.
- A feature that is itself a `<Converter>` or `<IntConverter>` can be written.
  A converter declares no `<AccessMode>`; it reads and writes through its
  `<pValue>`, but `effective_access_mode` reported it `RO` and `Camera::set`
  refused it with a type error, so `viva-camctl set` and Python's `set` could
  not write it either. `Camera::set` now writes through the converter's
  `<FormulaTo>`, after checking the converter's own `pIsAvailable` and
  `pIsLocked`. In the vendor corpus this is AVT Manta and Prosilica's
  `AcquisitionFrameRateAbs`; a `<Float>` that delegates to a converter, which
  is how most cameras model `ExposureTime` and `Gain`, was never affected.
- A feature reports no more access than its `<pValue>` chain allows. The new
  `NodeMap::declared_access_mode` combines the declared modes of every node
  along the chain: an `RO` anywhere removes writing, a `WO` removes reading,
  and a converter contributes nothing of its own. aravis takes the linked
  feature's mode instead. Before, a node that declares no `<AccessMode>` —
  and so defaults to `RW` — was reported `RW` over a read-only register:
  2,191 features in 37 of the 38 corpus documents, among them `WidthMax`,
  `GevCurrentIPAddress` and the `Chunk*` features, were offered as writable
  and refused at the register (2,178 now report `RO`, 13 `WO`).
  `effective_access_mode`, `viva-service`'s `FeatureState`, Studio and
  Python's node `access` build on it. `Node::access_mode` cannot see the chain
  and still answers for the node alone.

- `NodeMap::feature_state` no longer reads a feature that is not implemented
  or not available now — neither its value, its `<pMin>`/`<pMax>` nor its
  entries' predicates. GenApi forbids value access on such a node and cameras
  commonly refuse the read, which failed the whole snapshot, so a bulk read
  left the feature out instead of reporting it unavailable (Codex review of
  #169).

- `NodeMap::feature_state` reports no range for a feature with an unknown
  bound. The parser stands in `i64::MIN`/`i64::MAX` (`f64::MIN`/`f64::MAX` for a
  Float) for a bound the XML leaves out, and a `<pMin>`/`<pMax>` that is not
  read leaves that placeholder in place; both reached the wire as a range of
  about ±9.2e18 (Codex review of #170). The wire contract already said to omit
  the range instead.

### Viva Studio and documentation — not part of any published crate

Viva Studio lives in the `studio/` workspace. Its crates are not published to
crates.io; from this release its desktop bundles are attached to the GitHub
release. Nothing in this section changes the library.

- **The documentation is split by reader.** The book is the user guide, now in
  parts — getting started, using the library, Python, Viva Studio, help,
  reference — with a new **Viva Studio** chapter: installing a release bundle,
  first launch on each OS, connecting, features, images, reports and remote
  mode. Developer documentation lives in the repository: a new
  `CONTRIBUTING.md` (building, checks, test suites, the vendor corpus, pull
  requests), and `docs/` with an index. The book's "Running the tests" and
  "Contributing" pages moved there; its architecture page is rewritten for
  users, with USB3 Vision, the services and Python in the picture.
  `studio/README.md` keeps only what developers need, and the README is a
  user's landing page. A new test, `doc_links`, fails on any relative Markdown
  link that points at nothing (backlog CI-17).
- `docs/standards.md` and the book's `viva-gencp` page described GenCP as the
  protocol both GigE Vision and USB3 Vision speak, with register commands; GVCP
  is its own protocol, and GenCP has memory commands only.

- Studio builds on Tauri 2.12, React 19.3, Vite 8.3, Vitest 5 and
  TypeScript 7, and lints with Oxlint instead of ESLint: typescript-eslint
  refuses to load under TypeScript 7. The Oxlint configuration lists the same
  rules ESLint ran — 68 of the 69 recommended ESLint and typescript-eslint
  rules (`no-octal` is a TypeScript compile error anyway) and 14 of the 16
  React hooks and React Compiler rules (`config` and `gating` check compiler
  options the app does not set). A file of deliberate violations drew the same
  seven findings from both linters before ESLint was removed.
- **Studio snapshots are the image on screen.** A snapshot was the viewer's
  last WebSocket frame — a BMP file — read as raw pixels in the camera's
  format: the BMP header became the first row, Bayer and RGB frames were
  misread, and Mono10/12 saved nothing. The frame is now decoded as a BMP
  first. The PNG is the 8-bit image the viewer shows, not a raw-depth capture
  (ST-39).
- **Looking at a feature no longer queues a write.** Selecting a feature while
  connected copied its live value into a draft. Every one counted towards
  "Apply N", so a batch apply wrote back values the user had only looked at,
  possibly stale ones. An enumeration's draft took the wrong form, so its editor
  showed "(unset)" with a validation error until the user picked an entry. The
  editors now show the camera's value until the user edits it; the Boolean and
  String editors gain the same fallback. Preset import converts each entry by
  the feature's kind and leaves out read-only features, so an "Export State"
  file imports again. A batch apply that loses writes reports them.
- **The Image tab reports refused writes, and stops resetting what you type.**
  Its controls sent a failed write to the console only; it now appears as a
  toast, and ROI apply stops at the first refused write. Every slider field
  also re-synced from the camera whenever *any* feature changed, which reset a
  value mid-typing; each now follows its own feature and waits while its box
  has focus.
- **Ctrl+Enter on the Image tab no longer applies the Feature Browser's
  draft.** The Feature Browser kept its keyboard shortcuts while hidden, and
  Ctrl+Enter clicked its hidden Apply button, writing to the camera.
- **Studio no longer offers Record.** The button started a `.gsr` writer that
  never received a frame, so every recording held only a header. Recording
  returns together with playback (ST-10).
- **The UI has component tests and a linter.** Vitest runs `*.test.tsx` on
  jsdom with Testing Library and Tauri's IPC mock. The snapshot, draft,
  Image-tab and shortcut fixes above each come with a test that failed before
  the fix. ESLint runs typescript-eslint and
  react-hooks' `rules-of-hooks` and `exhaustive-deps`, in CI and in the quality
  gate. It found one latent defect: `TriggerSection` returned before calling
  its hooks. React 19 tolerates that today only because the early path calls
  no hooks at all.
- **Studio releases the camera on disconnect and at exit.** Disconnect only
  aborted the streaming tasks, and exit did nothing, because Tauri ends the
  process without dropping managed state; either way the camera kept
  acquiring and stayed claimed until its heartbeat expired, so an immediate
  reconnect could be refused. Both now stop the stream, send
  `AcquisitionStop`, release control privilege and drop the camera, each step
  best-effort with a short timeout. The first backend tests against
  `viva-fake-gige` cover both paths (ST-03).
- **Studio writes features that are converters** (see Fixed above for the
  library side): the UI model and the write pre-flight took a converter's
  access mode as a fixed `RO` and refused the write before it was sent.
- **The packet size can be set per camera** (ST-22, seen on hardware in
  #112). Studio negotiated the GVSP packet size from the host's MTU, and on a
  link whose real ceiling was lower it streamed nothing, with no way to say
  otherwise; `viva-camctl stream --packet-size` could. The acquisition section
  now offers Auto or a fixed size, kept per camera and used from the next
  start, in both modes.
- **One frame encoder, drawing only what can be seen** (ST-31, ST-32).
  Embedded and remote mode each turned frames into BMPs their own way, and
  the embedded one could not draw Mono10/12/14 or 16-bit Bayer. Both now use
  `viva_streamer::frame::FrameEncoder`, which reuses its buffers between
  frames and passes BGR through without swapping it twice. Embedded mode
  encodes at most 30 frames a second, and both modes only one a second while
  no viewer is connected — still keeping it, because the viewer connects after
  the acquisition starts and in SingleFrame mode that frame is the only one
  (Codex review of #173). Embedded mode warns once about a format it cannot
  draw rather than on every frame.
  When a frame's size or format changes mid-stream the viewer is told (ST-17).
- **Studio ships with each release** (ST-06). The release workflow builds
  unsigned bundles — a DMG for Apple Silicon, an AppImage and a deb for
  x86_64 Linux, an MSI for Windows — and attaches them to the GitHub release
  of every `v*` tag; until now every user built Studio from source. Studio
  takes the library's version (it said 0.1.0), and a test fails while its
  manifests disagree with the workspace. libusb is linked statically, so the
  bundles do not depend on one being installed. `studio/README.md` covers the
  first-launch prompts an unsigned app gets.
- **Every Studio command is permitted** (Codex review of #174). Tauri
  refuses an app command that no permission in `capabilities/main.json`
  allows, and five were in none: `generate_report`, so "Generate report"
  always failed; `backend_status`, so the header's mode chip and the warning
  for a `ZENOH_CONFIG` that fails to load (#132) could not appear; and the
  three IP configuration commands. Backlog ST-44 had this backwards, taking
  the permission sets for decoration. A test now checks every registered
  command against the sets, and another sends calls through Tauri's own ACL.
- **A report gets two minutes in remote mode** (Codex review of #174). The
  report query shared the 5-second timeout of a feature read, though the
  service reads the camera's whole XML to write it, and the cameras worth
  reporting on are the slow ones.
- **Dropped frames are shown** (ST-36). The header shows the camera's frame
  rate and, once there are any, the frames lost between camera and app — the
  symptom of a link problem like #112's. Embedded mode reported neither (the
  header read "Acquiring"), and remote mode's `dropped` was always 0.
- **The camera's identity and persistent IP** (ST-37). The Diagnostics tab
  shows the connected camera's vendor, model, serial, firmware, user ID, MAC
  and IP address — what a report asks for — and sets the persistent IP
  address the camera takes from its next restart.
- **USB3 Vision streams stop cleanly and keep their names** (Codex reviews of
  #179 and #180). Stopping waits for the USB reader, however long a read it is
  inside takes, so a restart or reconnect finds the endpoint free; it gave up
  after two seconds at first. A camera keeps its serial-based id in the device
  list when a later scan cannot read its serial, but only while it stays at
  the same USB position with the same vendor and product.
- **USB3 Vision cameras in embedded mode** (ST-14). Embedded mode discovered,
  opened and streamed only GigE Vision cameras, so a USB3 Vision camera
  needed `viva-service-u3v` and remote mode. The device list now includes
  them, told apart by serial (or bus position), and they read, write and
  stream like a GigE camera, and "Generate report" describes them (DX-06).
  The packet size and the IP configuration remain GigE Vision's.
- **The viewer shows the camera's pixels** (ST-39). The canvas held a copy
  downscaled to the window, so "1:1" and every zoom above fit enlarged that
  copy; it now holds every camera pixel and draws enlarged pixels as squares,
  and its size on screen is not rounded, so "1:1" is exactly one CSS pixel
  per camera pixel (Codex review of #178).
  The histogram shows its axis ends and the image's minimum, maximum, mean and
  share of samples at 255. Switching tabs no longer reconnects the stream or
  resets the zoom: the viewer stays mounted and skips drawing while hidden.
- **"Set IP…" for a camera on another subnet** (ST-37). Discovery finds such
  a camera but nothing can open it; the device list now offers FORCEIP, which
  gives it an address until it restarts, sent from the host address the camera
  answered at. Only `viva-camctl set-ip --force` could do this before. A
  camera one discovery scan misses keeps that address, rather than falling
  back to an interface the OS picks (Codex review of #177).
- **User sets** (ST-38). The Image tab's sidebar has a User Sets group:
  `UserSetSelector`, `UserSetLoad`, `UserSetSave`, and the default set under
  either SFNC name (`UserSetDefault` or `UserSetDefaultSelector`). Studio's own
  JSON presets hold no selector state; a user set is the camera's.
- **The Feature Browser reads only the rows on screen** (ST-40; Codex review
  of #172). Every row of a category or a search followed its feature's live
  state, so opening a category of hundreds of features, or searching broadly,
  read every one of them from the camera. Rows now read while in view. A
  search that matches more than 200 features says it shows the first 200,
  where it stopped silently.
- **The Feature Browser works from the keyboard** (ST-40). The arrow keys,
  Home and End move through the category and feature lists, the splitters
  resize with the arrow keys, and the breadcrumb shows every category between
  the root and the selected one. Muted text (`--text-muted`, about 80 rules)
  reached 2.3:1 against the background; it now meets WCAG AA's 4.5:1, and a
  test keeps it there.
- **Computed features show in the Feature Browser** (ST-34). A `<SwissKnife>`
  or `<IntSwissKnife>` became an `Unknown` node, which the category list
  skips, so none of the 55 listed under a category in the vendor corpus
  appeared there — `WidthMax`, `HeightMax` and `UserSetCurrent` among them. Each is now a
  read-only Float or Integer, as its output declares. `viva_xml_model` builds
  every node with one mapper where it had two near-identical 370-line copies;
  over the corpus the result is unchanged but for the SwissKnives. `UiNode`
  loses `raw`, which was always empty; `UiGraph.skipped` reports what the
  library could not build.
- **"Generate report" in the Diagnostics tab** (ST-41). Studio writes the
  report `viva-camctl report` writes — the same library code — and saves it
  to a file or copies it, with or without the camera's GenApi XML. In remote
  mode the service writes it, since the camera may not be reachable from the
  app. Every Studio user with a camera we cannot open can now send us what we
  ask for without installing the CLI.
- **Features the library dropped are named** (DX-05). Declarations in the XML
  that could not become features appear as warnings in the Feature Browser's
  Diagnostics tab, and the toolbar counts them ("· 2 not shown"), so a missing
  feature reads as dropped rather than absent.
- **Camera I/O no longer occupies the async runtime** (ST-31). Every embedded
  camera operation ran inside `block_in_place` under a `std::sync::Mutex`, so
  a command waiting for the camera held a runtime worker; the camera is now
  behind an async mutex and its I/O runs on the blocking pool.
- **One cache of live state, read only for what is on screen** (ST-29). The UI
  kept two half-migrated caches and read every feature of the camera at
  connect — hundreds, each several register reads — before showing anything.
  A single `FeatureStore` now reads a feature when a control first shows it,
  batched per tick, and keeps it current from the backend's events.
  "Export State" reads every feature when asked. Reads of one feature that
  answer out of order no longer let the older one land last (Codex review of
  #172).
- **Writes refresh what they change** (ST-30). After a write or command the
  features it invalidated are read again if they are on screen, so changing
  a selector updates the features it selects, and a lock shows as soon as it
  takes hold.
- **The Image tab's controls are drawn from the camera's state** (ST-29,
  ST-35). Six hand-written sections, with ranges and defaults made up in the
  UI (exposure 100–100000, gain 0–24, ROI 4096×3072), are replaced by one
  `<FeatureControl>` per feature in `sfnc-groups.json`, which takes its
  range, entries and access from the live state. A feature that is locked or
  unavailable is greyed out with the reason, here and in the Feature Browser;
  one the camera does not implement is not shown. The sidebar gains the
  frame-rate control, `TriggerSelector` and a `TriggerSoftware` button.
- **A field that only has focus no longer freezes** (Codex review of #167). The
  Image tab's fields stopped following the camera as soon as they had focus,
  and on blur wrote the stale value back; they now hold a value only once it
  is edited.
- **The UI follows the React Compiler's lint rules** (ST-43): ESLint runs the
  whole `react-hooks` preset. State that effects used to reset is now adjusted
  while rendering, and refs are no longer read or written during render.
- **The UI's IPC types are generated from the Rust ones** (ST-28). A test in
  the Tauri crate writes `ui/viva-studio-ui/src/generated/ipc.ts` with ts-rs —
  the `FeatureState` contract, the UiGraph, every command result and event
  payload, and a `StudioEvents` map from each event name to its payload — and
  fails while the committed file is stale; the hand-written copies are gone.
  Every event is now sent as a typed `StudioEvent` and received with
  `listenTo`, so a name cannot pair with the wrong shape. The honest types
  found one defect: "Export State" wrote a register's size summary into the
  preset as if it were a value.
- **Remote mode works through the same backend as embedded mode.** The commands
  used to branch on the mode, and remote mode lagged a contract version behind:
  it answered feature queries from a cache the connect-time read never filled,
  reporting every feature as `kind: "Unknown"` with no enumeration entries, and
  after a write it slept 50 ms and read that cache again. `RemoteBackend` now
  implements `DeviceBackend` like `EmbeddedBackend` does, and queries and
  follows the service's `FeatureState` topics, so both modes show the same
  `viva-genapi` state (ST-27). Disconnecting in remote mode now stops an
  acquisition the app started.
- **Writes and commands say what they invalidated.** After a write or command
  both modes emit `features-invalidated` with the features it may have changed
  (ST-30, backend half); the UI's re-read is the remaining half.
- **Exit no longer waits on a stuck release.** The exit hook awaited the
  camera's release in place, so a release blocked on the camera mutex or in
  device I/O kept the app open past its 3-second limit (Codex review of #168).
  The release now runs on its own task.
- **Backend tests run both modes end to end** against `viva-fake-gige`:
  embedded in-process, and remote through `viva-service` run in-process — the
  task set its binary runs — on a shared Zenoh session. They cover discovery,
  feature state, writes, invalidation, frames on the viewer's WebSocket,
  disconnect and exit (ST-03).
- **Gone:** `viva-mock-service` (a third copy of the Zenoh contract, behind it,
  ST-02), `viva-ws-streamer` (unused; the app embeds `viva_streamer`), the
  `studio/tests/e2e` crate that all but one test skipped, the `embedded_*` and
  `get_node_value`/`get_acquisition_status` commands, which nothing called,
  and — with the UI's single cache — `read_nodes_bulk`, `query_feature_state`
  and the legacy `NodeValueEntry` projection.
- **Embedded mode reports what the camera permits now.** Its feature state was
  a copy of `viva-service`'s that had fallen behind: it reported every feature
  available and implemented, ignored `pIsLocked`, and offered every
  enumeration entry the XML declares, including `PixelFormat` values the
  camera refuses (ST-18). It now calls `Camera::feature_state`, the
  computation the services use (ST-26). A test against `viva-fake-gige`,
  whose gates are registers, failed on each of the three before the switch.
- **Studio CI builds the Tauri app on Linux, Windows and macOS, and runs on
  library changes.** It used to compile the app on macOS only, which no known
  user runs, and to trigger only on `studio/` paths, so a library-only change
  could break Studio unseen (#105, repaired in #106).
- **Studio has a role and a plan**
  ([ADR-0024](../docs/adrs/adr0024-studio-reference-viewer.md)). It is the
  library's reference viewer: a single-camera tool to configure, view and
  diagnose a camera and to file a report, embedded mode first, with remote mode
  kept behind one backend trait. The backlog's ST section is rewritten from a
  review of the code and the eight reports Studio users have filed, and ordered
  by the ADR's phases. ST-01 is deleted, because #142 did it.
- **The Studio docs describe Studio as it is.** `docs/design.md`, `README.md`
  and `studio/CLAUDE.md` now name embedded mode, the primary path, rather than
  saying Studio only talks to the services over Zenoh.
  `docs/studio/testing-cookbook.md` drops the aravis prerequisites for the
  in-repo `viva-fake-gige`, lists the `FeatureState` topics, and says which
  Studio test suites run in CI and which do not. `studio/CLAUDE.md` no longer
  claims `RawNode` is populated (ST-34).
