# Backlog

Immediate, actionable tasks. The order of work lives in
[roadmap.md](roadmap.md); the [changelog](../CHANGELOG.md) records what
shipped. [Issue #191](https://github.com/VitalyVorobyev/viva-genicam/issues/191)
is the public list of these gaps: the PR that ships a row ticks or updates its
item there.

**Legend**

- Priority: **P0** (do next) / **P1** (soon) / **P2** (when convenient)
- Size: **S** (hours) / **M** (a day or two) / **L** (several days) /
  **XL** (a week+)
- Status: `planned` / `in-progress` / `blocked`
- Notes open with the [roadmap](roadmap.md) milestone that ships the row
  (`**Milestone X.**`), or with **Waiting on hardware** or **Not planned for
  0.9.0**; a row with none of these is unscheduled.

Every row carries its evidence — a corpus count, a code symbol, or an issue
number — so priority can be argued from data rather than from intuition
([ADR-0018](adrs/adr0018-genapi-conformance-over-convenience.md)).

**This file only lists open work.** Delete a row in the PR that ships it; the
[changelog](../CHANGELOG.md) records what shipped and why.

Filing rules:

- **Do not propose downgrading a log level before the warning's cause is known** — that deletes the evidence.
- **A row filed from fake-camera output or from reading code and specifications is a hypothesis** until real hardware shows the same thing.

## TC — Transport conformance (ADR-0019)

| TC-05 | Accept the payload types cameras actually send | P1 | M | planned | **Milestone R.** `parse_leader` (`crates/viva-gige/src/gvsp.rs`) reads the payload type as `get_u16() as u8`, so Image Extended Chunk `0x4001` is stored as plain image `0x01` and the chunk bit is lost; types whose low byte is not `0x01` (`0x0002` raw data, `0x0003` file, `0x0004` chunk data) and packet format `0x04` (single-packet block) are rejected. | TC-06 | Chunk trailer layout is self-consistent, not conformant | P1 | M | planned | **Milestone C.** `viva_gige::gvsp::parse_chunks` decodes front-to-back `[id][reserved][len][data]` big-endian, while `decode_known` in `crates/viva-genicam/src/chunks.rs` reads values little-endian. A capture from a camera that actually sends one decides it — and if a real device puts the timeout in the full `u32`, that device wins. The capture needs `PENDING_ACK` enabled first: we never set its enable bit (bit 1, `0x2`) in GVCP Configuration `0x0954`, so a compliant device may never send one (TC-30) |
| TC-16 | Per-transport status-code types | P2 | M | planned | **Milestone X.** GVCP and GenCP share `0x0000`, `0x8001`-`0x8007` and `0x8FFF` but conflict at `0x800B` (`NO_MSG` vs `MSG_TIMEOUT`), and each owns codes the other lacks. A transport-specific code decodes as `StatusCode::Unknown(raw)` — reportable but unnamed; no current path decodes `0x800B`. **Scope**: [ADR-0020](adrs/adr0020-per-transport-status-codes.md) (Proposed) points 1-2, a shared core plus per-transport types |
| TC-21 | `BAD_ALIGNMENT` on a real camera's event registers | **P1** | M | planned | **Milestone C.** **Seen on hardware** ([#112](https://github.com/VitalyVorobyev/viva-genicam/issues/112), Studio log): 62 reads of `pEventStream*Reg` on a Vieworks FS3200T return `BAD_ALIGNMENT (0x8005)`. `GigeDevice::read_mem` rounds the *count* to a multiple of four ([#35](https://github.com/VitalyVorobyev/viva-genicam/issues/35)); nothing checks the *address*. | TC-24 | Settle in-flight heartbeats (ADR-0023) against hardware | P2 | S | planned | **Waiting on hardware.** [#164](https://github.com/VitalyVorobyev/viva-genicam/pull/164) sends READREG/READMEM(CCP) while a command is still outstanding, once an ACK wait outlasts the keepalive period — in practice only during `PENDING_ACK` extensions or a raised `set_control_timeout`. The only evidence is [#163](https://github.com/VitalyVorobyev/viva-genicam/issues/163)'s UDP fixture, which expires CCP during a pending operation by construction. Open: does a real device run its heartbeat timer while it processes a `PENDING_ACK`ed command, and how does it answer a second command meanwhile (ACK, `BUSY`, silence)? aravis sends nothing in between: its heartbeat thread waits on the I/O mutex held across the whole ACK wait (`arvgvdevice.c:179–325`). | TC-26 | Three loose ends in the in-flight heartbeat path | P2 | S | planned | **Milestone L.** Found reviewing [#164](https://github.com/VitalyVorobyev/viva-genicam/pull/164). (1) A failed probe *send* returns `AckRecv::Io` from `recv_for_request` (`crates/viva-gige/src/gvcp.rs`), which `transact_with_retry` treats as a receive error and answers by resending the **active** command — possibly a non-idempotent write the device has already `PENDING_ACK`ed. ## SR — Streaming reliability

| ID | Task | Priority | Size | Status | Notes |
|----|------|----------|------|--------|-------|
| SR-03 | Per-stream ephemeral ports + `source_filter` enforcement | P0 | M | planned | **Milestone S.** Every stream binds port `0x5FFF` by default (`crates/viva-genicam/src/stream.rs:753`) with `SO_REUSEPORT` (`crates/viva-gige/src/nic.rs:487`), so two streams on one host can share the port and split each other's datagrams; aravis binds port 0. The rustdoc on `StreamBuilder::destination_port` (`:692`) says the default is 0, "device chosen", which the code does not do. `StreamConfig::source_filter` is set in `StreamBuilder::build` and never read, because `PacketSource::recv` discards the source address — and it holds the host's own address, not the camera's. Bind port 0 by default, enforce the camera as source, and keep `destination_port(n)` for firewalls |
| SR-04 | Packet resend: the spec's request, wired into the receive engine | P1 | L | planned | **Milestone S.** `GigeDevice::request_resend` (`crates/viva-gige/src/gvcp.rs:1628`) sends 8 bytes `[block u16][0 u16][first u16][last u16]` from the control socket with `ACK_REQUIRED` and waits for `0x0041`; Wireshark's `packet-gvcp.c` and aravis (`arv_gvcp_packet_new_packet_resend_cmd`) both use 12 bytes `[channel u16][block u16][first u32][last u32]` with 24-bit packet IDs (20 with extended IDs, flag `0x10`), and aravis asks for no ACK, sends from the stream socket and checks capability bit `0x4` of `0x0934` (TC-30). `ResendPlanner`, `request_resend` and `StreamConfig::resend_enabled` have no production caller; the only test (`crates/viva-gige/tests/inflight_keepalive.rs:88`) uses a responder that ACKs, and `viva-fake-gige` ignores PACKETRESEND. No camera has exercised resend, so the telemetry side (SR-07) reads 0 |
| SR-07 | Honest streaming telemetry | P1 | M | planned | **Milestone R.** `StreamStats` (`crates/viva-gige/src/stats.rs`) has no count of missing, duplicate, ignored or malformed packets, and a frame lost whole — visible only as a block-ID gap — is not counted; GVSP parse errors in `FrameStream` are dropped at `trace`. `record_resend`, `record_resend_ranges`, `record_late_frame` and `record_pool_exhaustion` have no production caller (only `examples/stats.rs`, which fabricates them), so `resends=0` means "not implemented", not "healthy"; until fixed, `drops` is the only figure worth reading. aravis keeps 17 counters (`arvgvstream.c` ~1685-1720) |
| SR-08 | IGMP leave on multicast stream teardown | P2 | S | planned | **Milestone L.** `nic::bind_multicast` / `nic::join_multicast` (`crates/viva-gige/src/nic.rs`) join the group; nothing ever leaves it |
| SR-09 | Delete or wire the unused reassembly stack | P2 | M | planned | **Milestone R.** Part of API-01, which owns the scope: `Reassembler`, `FrameAssembly`, `FrameQueue`, `BufferPool` and `GigeDevice::negotiate_stream` have no callers |
| SR-12 | Per-packet `HashSet` insert on the receive hot path | P2 | S | planned | **Milestone R.** `FrameAssemblyState::received_packet_ids` (`crates/viva-genicam/src/stream.rs`) is a `HashSet<u32>` taking one insert per datagram; at a 1500-byte packet size a 3.1 MB frame costs ~2 100 hashes. A grow-only bitmap or a max-ID watermark does the same job allocation-free. The data structure is chosen in API-01; this row keeps it from being lost if API-01 slips |
| SR-13 | The frame timeout counts from the leader, not the last packet | P0 | M | planned | **Milestone R.** `DEFAULT_FRAME_TIMEOUT` is 100 ms (`crates/viva-genicam/src/stream.rs:1006`) and `is_expired` measures it from `started`, set at the leader (`:1130`); no caller overrides it. So a frame whose transfer takes longer than 100 ms never completes: by arithmetic ≈12 MB at 1 Gb/s, less on a link throttled by `GevSCPD` or a throughput limit. aravis measures from the last packet received (`_check_frame_completion`, `arvgvstream.c:788`) |
| SR-14 | Packet offsets ignore the extended-ID header | P0 | M | planned | **Milestone R.** `gvsp_payload_size` subtracts a fixed 8-byte `GVSP_HEADER_SIZE` (`crates/viva-genicam/src/stream.rs:1009-1023`) and the assembler writes packet `n` at `(n-1) * packet_payload_size` (`:1096`), but the extended-ID header is 20 bytes (`crates/viva-gige/src/gvsp.rs:200`), so on Linux and macOS packet `n` lands 12·(n−1) bytes too far. The Windows receiver appends in arrival order and is unaffected; no fake sends extended IDs. aravis takes the overhead per packet (`ARV_GVSP_PACKET_PROTOCOL_OVERHEAD(ext_ids)`, `arvgvspprivate.h:264`) |
| SR-15 | No receive thread on Linux and macOS | P1 | L | planned | **Milestone R.** Packets are read only inside `FrameStream::next_block()` (`crates/viva-genicam/src/stream.rs:1510`), so time the application spends on a frame becomes datagrams the kernel drops, which no counter sees. Windows already reads on its own thread ([#72](https://github.com/VitalyVorobyev/viva-genicam/pull/72)). One `std::thread` per stream on every OS, with a `next_block_blocking(timeout)` beside the async front end (ADR-0025, to be written) |
| SR-16 | `SO_RCVBUF` is fixed, and a kernel cap goes unreported | P1 | S | planned | **Milestone R.** The stream socket asks for a fixed 4 MiB (`DEFAULT_RCVBUF_BYTES`, `crates/viva-gige/src/nic.rs:28`) and logs what the kernel granted only at `debug!` (`:489-494`); the multicast path never reads it back (`:549`). aravis sizes the buffer to the frame and warns. Request max(4 MiB, 2 × payload), read back the grant, and warn once, naming `net.core.rmem_max` / `kern.ipc.maxsockbuf` |
| SR-17 | Four hand-written reassemblers on the raw stream socket | P1 | M | planned | **Milestone R.** `viva-camctl bench` (`crates/viva-camctl/src/cmd_bench.rs:135-190`) and the examples `soak_bench`, `grab_with_chunks` and `multicast_grab` read datagrams through `Stream::socket()` / `FrameStream::socket()` (`crates/viva-genicam/src/stream.rs:958`, `:1482`) and append payloads in arrival order; `bench` counts every trailer as a frame even when packets were lost. Move them onto the engine with API-01 and delete the accessors |
| SR-18 | `Frame` has no block ID or status; early trailers and repeated leaders lose frames | P1 | M | planned | **Milestone R.** `Frame` (`crates/viva-genicam/src/frame.rs:13-28`) carries no `block_id`, payload type or completeness, and an incomplete frame cannot be delivered even on request. A trailer that overtakes the last payload packet drops the frame (`stream.rs:1645-1655`), and a repeated leader restarts the assembly even for the same block (`:1583-1604`). Add `block_id`, the `u16` payload type (TC-05) and a status (complete, incomplete, device status, trailer missing), with incomplete delivery opt-in |
| SR-19 | `GevSCPD` is written at every stream start, in the wrong unit | P1 | S | planned | **Milestone S.** `StreamBuilder::build` always writes `GevSCPD` (`crates/viva-genicam/src/stream.rs:860-875`): the caller's value, else `2000 / 80` = 25 for packets of 1 500 bytes or less and 0 above, overwriting the user's tuning. That assumes 80 ns units; the register counts timestamp ticks (frequency at `0x093C`/`0x0940`). aravis never writes it at stream setup and converts nanoseconds to ticks (`arv_camera_gv_set_packet_delay`) |
| SR-20 | Multicast: no receive-only monitor; the raw-register fallback writes the port into the wrong half | P1 | M | planned | **Milestone L.** A second host cannot watch a multicast stream: opening claims control unconditionally (`crates/viva-genicam/src/lib.rs:1162`) and stream setup writes `GevSCPD` (`stream.rs:872`), and both need control (TC-29). When the SFNC nodes are missing, `configure_stream_multicast` writes a 2-byte port into the 32-bit stream channel port register (`lib.rs:696-699`), so it lands in the high half — the bug already fixed for `GevMCP` (`events.rs:92`) |
| SR-21 | `GevStreamChannelCount` is never checked | P2 | S | planned | **Milestone S.** Nothing reads `GevNumberOfStreamChannels` (`0x0904`) before configuring a channel; only the report dumps it (`crates/viva-genicam/src/report.rs:144`). A channel index the camera lacks is configured anyway instead of refused with a clear error. Spec-derived |
| SR-22 | The Windows stream reader stops on any non-timeout error | P1 | S | planned | **Milestone S.** The Windows receiver ends the stream on any socket error other than `WouldBlock`/`TimedOut`/`Interrupted` (`crates/viva-genicam/src/stream.rs:1221-1236`).
