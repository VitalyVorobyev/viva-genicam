# Backlog

Immediate, actionable tasks. The order of work lives in
[roadmap.md](roadmap.md). [Issue #191](https://github.com/VitalyVorobyev/viva-genicam/issues/191)
is the public list of these gaps: the PR that ships a row ticks or updates its
item there.

**Legend**

- Priority: **P0** (do next) / **P1** (soon) / **P2** (when convenient)
- Size: **S** (hours) / **M** (a day or two) / **L** (several days) /
  **XL** (a week+)
- Status: `planned` / `in-progress` / `blocked`
- Notes open with **Waiting on hardware**, **Not planned**, or a Studio
  phase ([ADR-0024](adrs/adr0024-studio-reference-viewer.md)); a row with
  none of these is unscheduled.

Every row carries its evidence — a corpus count, a code symbol, or an issue
number — so priority can be argued from data rather than from intuition
([ADR-0018](adrs/adr0018-genapi-conformance-over-convenience.md)).

**This file only lists open work.** Delete a row in the PR that ships it; the
[changelog](../CHANGELOG.md) records what shipped and why.

Filing rules:

- **Do not propose downgrading a log level before the warning's cause is known** — that deletes the evidence.
- **A row filed from fake-camera output or from reading code and specifications is a hypothesis** until real hardware shows the same thing.

| SR-23 | Confirm the receive engine's restart, late-window and oversized-packet rules on hardware | P2 | S | planned | **Waiting on hardware; partly answered.** Derived from aravis and arithmetic, verified on the fake ([ADR-0025](adrs/adr0025-gvsp-receive-engine.md)): a block id up to 100 behind the newest is late; a *leader* of block 1 from anything but its predecessor is a restart; a data packet longer than the stride is refused, not written; the newest block does not time out while only its leader has arrived; the 100 ms inactivity default. An Allied Vision Manta G-125B (firmware 00.01.44.28514) exercised none of the first three: its block ids ran on across 100 AcquisitionStop/Start in one stream (303 frames, ids 1 to 303, none missed or incomplete) and across `PixelFormat` and `Width` changes between rounds, and started at 1 only in a new control session; asked for 1600- and 9000-byte packets on a 1500-byte link, the probe bisected both down to 1500 and the stream ran complete; and a `GevSCPSPacketSize` written during acquisition stopped its stream (the block cut short, nothing after), so it cannot be made to send packets longer than the stride. **Next step**: a camera whose block ids restart at 1 on AcquisitionStart, and one whose packet size the host misjudges while it streams |
| SR-25 | The standard-id resend request's first word, and other cameras' answers | P2 | S | planned | **Waiting on hardware; partly answered.** An Allied Vision Manta G-125B (firmware 00.01.44.28514) resent with status `0x0000`, not `0x0100`, and answered every packet it could not serve — of a block about 23 frames old, past a block's end, of a block not yet sent — with a header-only GVSP packet of its own: status `0x800C`, data packet format, that packet's block and id (from a raw socket); a request for a whole block (851 packets) was served in full. The engine handles each refused packet individually, retaining retries for higher and lower neighbours, with duplicate-safe counters (`an_unavailable_answer_per_packet_is_counted_once`, `a_packet_refusal_does_not_cancel_its_neighbours_recovery`); an all-previous answer clips at the named id. The fake answers per packet too. Open: (1) the standard-id request's first word — Wireshark reads `[channel u16][block u16]`, aravis writes the block id across the whole word, so they agree only on channel 0, the Manta's only channel; (2) whether other cameras send `0x8011`/`0x8012`, answer per range, or stay silent. **Next step**: a camera with two stream channels, and a `-vv` log of a lossy stream from another vendor |
| SR-27 | Every frame is a fresh allocation | P2 | M | planned | **Hypothesis.** The receive engine takes each block's buffer from `BufferSource`, whose only implementation is `Allocate`: a zeroed `vec![0; len]` per frame (`crates/viva-genicam/src/stream/assembly.rs`). No pool exists and none is offered to the caller. | GT-04 | GenTL events beyond `EVENT_NEW_BUFFER` | P2 | M | planned | **Not planned.** `GCRegisterEvent` accepts only `EVENT_NEW_BUFFER` on a data stream; any other type is `GC_ERR_NOT_IMPLEMENTED`, which GenTL 1.6 §4.2.1 allows ("There are no mandatory event types"). ## UV — USB3 Vision

| ID | Task | Priority | Size | Status | Notes |

| UV-05 | Which transfer errors a camera recovers from | P2 | M | blocked | **Waiting on hardware.** A failed transfer gives up its block, resets the endpoint and goes on; eight in a row end the stream (`MAX_CONSECUTIVE_FAILURES`, `crates/viva-u3v/src/stream.rs`). Not seen in a real report yet. ## DC — Device classes beyond area-scan

A laser profile scanner (Micro-Epsilon scanCONTROL 850050, [#93](https://github.com/VitalyVorobyev/viva-genicam/pull/93)) is in the corpus and `viva-pfnc` has its `Coord3D_*` codes, but nothing above `viva-pfnc` knows what a `Coord3D_*` frame is. Rows are scheduled only when verified against code or a wire capture, never against our idea of what a 3D camera sends.

| ID | Task | Priority | Size | Status | Notes |
|----|------|----------|------|--------|-------|
| DC-02 | The Zenoh frame header has no code for the scanCONTROL's formats | P2 | M | planned | **Waiting on hardware.** `ImageMeta` names any PFNC format, `Coord3D_*` included, and sizes it from the camera's `PayloadSize` (`image_meta`, `crates/viva-service/src/acquisition.rs`). The 16-byte frame header carries a one-byte code (`WIRE_CODES`, `crates/viva-zenoh-api/src/frame_header.rs`) whose one 3D entry, `Coord3D_C16`, the scanCONTROL does not advertise, so its frames go out with code 0. Adding codes changes the frame header — a wire-format change; land it with DC-03 |
| DC-03 | No `Scan3d*` SFNC constants, so a `Coord3D` payload cannot be interpreted | P2 | M | planned | **Waiting on hardware.** `viva-sfnc` has no `Scan3d*` constants and no Rust source reads `Scan3d`, so a `Coord3D_AC16` buffer is raw integers with no metric meaning or invalid-point mask. `MicroEpsilon_scanCONTROL_850050.xml:6104+` declares `Scan3dCoordinateScale`/`Offset`/`Selector`, `Scan3dInvalidDataFlag`/`Value` and `Scan3dOutputMode`, applying scale and offset only to `Coord3D_AC16` (`:6188`, `:6218`); `DeviceScanType` (`:40-61`) offers `Areascan3D`/`Linescan3D`. On the wire `Scan3dInvalidDataValue` is LE `f32` `ff ff ff 7e` = `1.7014117e38`, matching the node ([#93 capture](https://github.com/VitalyVorobyev/viva-genicam/pull/93#issuecomment-5162882332)). The nodes already parse as `Float`/`Enumeration`; add constants and a reader |
| DC-04 | No fake can emit a `Coord3D_*` frame | P2 | M | planned | **Waiting on hardware.** `viva-fake-gige` can send payload type `0x4001` and sizes images by PFNC bit depth, but `viva-fake-u3v`'s `bytes_per_pixel` knows only RGB8 = 3, else 1, so DC-02/DC-03 have no end-to-end test. **Wire facts** (scanCONTROL 850050, [#93 capture](https://github.com/VitalyVorobyev/viva-genicam/pull/93#issuecomment-5162882332)): leader payload type `0x4001` (image + extended chunk; not GenDC, not multipart), PFNC `0x026000C0`; coordinates little-endian, interleaved per point, 4 / 4 / 8 / 12 bytes for `Coord3D_C32f` / `_AC16` / `_AC32f` / `_ABC32f` (matching `viva_pfnc::PixelFormat::bytes_per_pixel`); in the four decoded `(A, B, C)` tuples `B` is zero for a single profile. **Next step**: build the fake from that capture |
| DC-05 | Event-vision blocks: a Python `next_block` | P2 | S | planned | **Waiting on hardware.** From [#138](https://github.com/VitalyVorobyev/viva-genicam/issues/138) / [#139](https://github.com/VitalyVorobyev/viva-genicam/pull/139) (Lucid Triton2 EVS, Sony IMX636); the service already publishes event blocks on `genicam/devices/{id}/evs`. Remaining: (1) `viva-pygenicam` exposes only `next_frame`, so Python receives an event block as a 1 × N frame; (2) only the fake has delivered an event block through the receive engine |
| DC-06 | `viva-camctl stream --raw-out` edge cases | P2 | S | planned | **Waiting on hardware.** From reviewing [#154](https://github.com/VitalyVorobyev/viva-genicam/pull/154). (1) The file is opened with `append(true)` (`crates/viva-camctl/src/cmd_stream.rs`), so reruns concatenate captures, even of different EVT formats; truncate by default with an explicit `--append`, or refuse a format change. (2) `--save` defaults to 1 (`crates/viva-camctl/src/cli.rs`), so `--raw-out` still writes a `block_0001.*`. (3) The file is created before the first block, so an image stream leaves an empty file |
