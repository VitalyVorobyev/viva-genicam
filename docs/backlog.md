# Backlog

Immediate, actionable tasks. The order of work lives in
[roadmap.md](roadmap.md); the [changelog](../CHANGELOG.md) records what
shipped. [Issue #191](https://github.com/VitalyVorobyev/viva-genicam/issues/191)
is the public list of these gaps: the PR that ships a row ticks or updates its
item there.

**Legend**

- Priority: **P0** (do next) / **P1** (soon) / **P2** (when convenient)
- Size: **S** (hours) / **M** (a day or two) / **L** (several days) /
  **XL** (a week+)
- Status: `planned` / `in-progress` / `blocked`
- Notes open with the [roadmap](roadmap.md) milestone that ships the row
  (`**Milestone X.**`), or with **Waiting on hardware** or **Not planned for
  0.9.0**; a row with none of these is unscheduled.

Every row carries its evidence — a corpus count, a code symbol, or an issue
number — so priority can be argued from data rather than from intuition
([ADR-0018](adrs/adr0018-genapi-conformance-over-convenience.md)).

**This file only lists open work.** Delete a row in the PR that ships it; the
[changelog](../CHANGELOG.md) records what shipped and why.

Filing rules:

- **Do not propose downgrading a log level before the warning's cause is known** — that deletes the evidence.
- **A row filed from fake-camera output or from reading code and specifications is a hypothesis** until real hardware shows the same thing.

## UV — USB3 Vision

USB3 Vision streaming and device handling. One camera has run it (TC-27, [ADR-0032](adrs/adr0032-usb3-vision-transport.md) §8); what that camera could not show is below.

| ID | Task | Priority | Size | Status | Notes |
|----|------|----------|------|--------|-------|
| UV-05 | Which transfer errors a camera recovers from | P2 | M | blocked | **Waiting on hardware.** A failed transfer gives up its block, resets the endpoint and goes on; eight in a row end the stream (`MAX_CONSECUTIVE_FAILURES`, `crates/viva-u3v/src/stream.rs`). None of that has met a real failure: the camera never stalled, and only the fake and the mock exercised it. Open: which errors are transient on Linux and Windows; whether a camera restarts its block ids at 0 after a reset in the middle of a stream, as it does after a reset before enabling (the facade counts a lower id as a restart, not a gap); and what macOS reports for a stall, since it reports a transfer it aborted as `Cancelled`. An unplug on macOS reports `kIOReturnNotResponding`, not `kIOReturnNoDevice` (TC-27 (5)), so an unknown error is checked against the device list before it is recovered from; whether a `kIOReturnNotResponding` on a device still listed is ever transient is open too. A `-vv` log of a stream that hit one settles it |
| UV-06 | An event that asks for an acknowledgement | P2 | S | blocked | **Waiting on hardware.** A GenCP `EVENT_CMD` may set `RequestAck`. The USB3 Vision event interface has only an IN endpoint, so the host has nowhere to send an `EVENT_ACK`; `U3vEventStream` logs it once and carries on (`crates/viva-u3v/src/event.rs`). The mvBlueFOX3-2004G never set it. A camera that does, and what it does when no acknowledgement comes, settles whether it needs anything more |
| UV-07 | A claim error's hint repeats its cause in `report` | P2 | S | planned | Codex on [#208](https://github.com/VitalyVorobyev/viva-genicam/pull/208): `U3vError::Claim` prints `{source}; {hint}` (`crates/viva-u3v/src/lib.rs`), and `error_line` (`crates/viva-camctl/src/common.rs`) drops a cause only when the message before it ends with that cause, so with the Windows WinUSB hint `viva-camctl report --usb` prints the nusb message twice (`…: could not determine driver for interface; <hint>: could not determine driver for interface`). Not seen in a real report yet. Either keep the source last in the message, or teach the chain walk to drop a cause the message contains anywhere; cover the hinted case in `an_error_chain_does_not_repeat_what_a_display_already_said` |

## DC — Device classes beyond area-scan

A laser profile scanner (Micro-Epsilon scanCONTROL 850050, [#93](https://github.com/VitalyVorobyev/viva-genicam/pull/93)) is in the corpus and `viva-pfnc` has its `Coord3D_*` codes, but nothing above `viva-pfnc` knows what a `Coord3D_*` frame is. Rows are scheduled only when verified against code or a wire capture, never against our idea of what a 3D camera sends.

| ID | Task | Priority | Size | Status | Notes |
|----|------|----------|------|--------|-------|
| DC-02 | The Zenoh frame header has no code for the scanCONTROL's formats | P2 | M | planned | **Waiting on hardware.** Since API-10 `ImageMeta` names any PFNC format, `Coord3D_*` included, and sizes it from the camera's `PayloadSize` (`image_meta`, `crates/viva-service/src/acquisition.rs`). The 16-byte frame header still carries a one-byte code (`WIRE_CODES`, `crates/viva-zenoh-api/src/frame_header.rs`) whose one 3D entry, `Coord3D_C16`, the scanCONTROL does not advertise, so its frames go out with code 0. Adding codes changes the frame header — a wire-format change; land it with DC-03 |
| DC-03 | No `Scan3d*` SFNC constants, so a `Coord3D` payload cannot be interpreted | P2 | M | planned | **Waiting on hardware.** `viva-sfnc` has no `Scan3d*` constants and no Rust source reads `Scan3d`, so a `Coord3D_AC16` buffer is raw integers with no metric meaning or invalid-point mask. `MicroEpsilon_scanCONTROL_850050.xml:6104+` declares `Scan3dCoordinateScale`/`Offset`/`Selector`, `Scan3dInvalidDataFlag`/`Value` and `Scan3dOutputMode`, applying scale and offset only to `Coord3D_AC16` (`:6188`, `:6218`); `DeviceScanType` (`:40-61`) offers `Areascan3D`/`Linescan3D`. On the wire `Scan3dInvalidDataValue` is LE `f32` `ff ff ff 7e` = `1.7014117e38`, matching the node ([#93 capture](https://github.com/VitalyVorobyev/viva-genicam/pull/93#issuecomment-5162882332)). The nodes already parse as `Float`/`Enumeration`; add constants and a reader |
| DC-04 | No fake can emit a `Coord3D_*` frame | P2 | M | planned | **Waiting on hardware.** `viva-fake-gige` can send payload type `0x4001` and sizes images by PFNC bit depth, but `viva-fake-u3v`'s `bytes_per_pixel` knows only RGB8 = 3, else 1, so DC-02/DC-03 have no end-to-end test. **Wire facts** (scanCONTROL 850050, [#93 capture](https://github.com/VitalyVorobyev/viva-genicam/pull/93#issuecomment-5162882332)): leader payload type `0x4001` (image + extended chunk; not GenDC, not multipart), PFNC `0x026000C0`; coordinates little-endian, interleaved per point, 4 / 4 / 8 / 12 bytes for `Coord3D_C32f` / `_AC16` / `_AC32f` / `_ABC32f` (matching `viva_pfnc::PixelFormat::bytes_per_pixel`); in the four decoded `(A, B, C)` tuples `B` is zero for a single profile. **Next step**: build the fake from that capture |
| DC-05 | Event-vision blocks: a Python `next_block` | P2 | S | planned | **Waiting on hardware.** From [#138](https://github.com/VitalyVorobyev/viva-genicam/issues/138) / [#139](https://github.com/VitalyVorobyev/viva-genicam/pull/139) (Lucid Triton2 EVS, Sony IMX636); the service already publishes event blocks on `genicam/devices/{id}/evs`. Remaining: (1) `viva-pygenicam` exposes only `next_frame`, so Python receives an event block as a 1 × N frame; (2) only the fake has delivered an event block through the receive engine |
| DC-06 | `viva-camctl stream --raw-out` edge cases | P2 | S | planned | **Waiting on hardware.** From reviewing [#154](https://github.com/VitalyVorobyev/viva-genicam/pull/154). (1) The file is opened with `append(true)` (`crates/viva-camctl/src/cmd_stream.rs`), so reruns concatenate captures, even of different EVT formats; truncate by default with an explicit `--append`, or refuse a format change. (2) `--save` defaults to 1 (`crates/viva-camctl/src/cli.rs`), so `--raw-out` still writes a `block_0001.*`. (3) The file is created before the first block, so an image stream leaves an empty file |
