# Backlog

Immediate, actionable tasks. The order of work lives in
[roadmap.md](roadmap.md); the [changelog](../CHANGELOG.md) records what
shipped. [Issue #191](https://github.com/VitalyVorobyev/viva-genicam/issues/191)
is the public list of these gaps: the PR that ships a row ticks or updates its
item there.

**Legend**

- Priority: **P0** (do next) / **P1** (soon) / **P2** (when convenient)
- Size: **S** (hours) / **M** (a day or two) / **L** (several days) /
  **XL** (a week+)
- Status: `planned` / `in-progress` / `blocked`
- Notes open with the [roadmap](roadmap.md) milestone that ships the row
  (`**Milestone X.**`), or with **Waiting on hardware** or **Not planned for
  0.9.0**; a row with none of these is unscheduled.

Every row carries its evidence — a corpus count, a code symbol, or an issue
number — so priority can be argued from data rather than from intuition
([ADR-0018](adrs/adr0018-genapi-conformance-over-convenience.md)).

**This file only lists open work.** Delete a row in the PR that ships it; the
[changelog](../CHANGELOG.md) records what shipped and why.

Filing rules:

- **Do not propose downgrading a log level before the warning's cause is known** — that deletes the evidence.
- **A row filed from fake-camera output or from reading code and specifications is a hypothesis** until real hardware shows the same thing.

## TC — Transport conformance (ADR-0019)

The GVCP/GVSP audit ADR-0018 never reached. Opcodes cross-checked against
`../aravis/src/arvgvcpprivate.h`.

| ID | Task | Priority | Size | Status | Notes |
|----|------|----------|------|--------|-------|
| TC-10 | `viva-gencp::encode_cmd` is dead *and* divergent | P2 | S | planned | **Milestone X.** It writes a different header shape (no `0x42` key byte) than `viva-gige` actually uses, and has no callers outside its own tests and README (`crates/viva-gencp/src/lib.rs`) |
| TC-12 | Settle the GVCP `PENDING_ACK` field width against hardware | P2 | S | planned | **Waiting on hardware.** GigE Vision 1.2 §18.5 defines 2 reserved bytes + a `u16` `time_to_completion`; aravis reads all four payload bytes as a big-endian `u32`. The readings agree only while `reserved` is zero. `parse_pending_ack` (`crates/viva-gige/src/gvcp.rs`) implements the spec `u16`. A capture from a camera that actually sends one decides it — and if a real device puts the timeout in the full `u32`, that device wins. `PENDING_ACK` is enabled at open where GVCP Capability offers it (bit `0x2` of GVCP Configuration `0x0954`), so a `-vv` log or a capture of one slow command now shows it. The reporter on [#163](https://github.com/VitalyVorobyev/viva-genicam/issues/163#issuecomment-6118461248) has a control-only capture of a scanCONTROL 8500-50 command that sends five `PENDING_ACK`s (`DebugPendingAckTest`); it settles the width |
| TC-16 | Per-transport status-code types | P2 | M | planned | **Milestone X.** GVCP and GenCP share `0x0000`, `0x8001`-`0x8007` and `0x8FFF` but conflict at `0x800B` (`NO_MSG` vs `MSG_TIMEOUT`), and each owns codes the other lacks. A transport-specific code decodes as `StatusCode::Unknown(raw)` — reportable but unnamed; no current path decodes `0x800B`. **Scope**: [ADR-0020](adrs/adr0020-per-transport-status-codes.md) (Proposed) points 1-2, a shared core plus per-transport types |
| TC-21 | `BAD_ALIGNMENT` on a real camera's event registers | **P1** | S | blocked | **Waiting on hardware.** **Seen on hardware** ([#112](https://github.com/VitalyVorobyev/viva-genicam/issues/112), `studio-run.log`): 62 reads on a Vieworks FS3200T fail with `BAD_ALIGNMENT (0x8005)`, and all 62 are SFNC event-data features and their registers — `EventLine{1,2,3,4,5,6,8,10}{Rising,Falling}Edge` and `EventStream{0,1,2}{AcquisitionTrigger,ExposureStart,ExposureEnd,FrameStart,FrameEnd}`, each with its `p…Reg`. **Inferred, not confirmed** (the camera's XML is neither in the corpus nor on the issue): in every corpus document that declares such features, the event ID is a 2-byte register at 0x2 and the timestamp an 8-byte register at 0x8 *on an event port*; read from device memory, the first is an unaligned `READMEM` and the second returns bootstrap bytes — the same log's `…TimestampReg` values exceed `i64::MAX`. Since ADR-0026 no register on an event port reads device memory, so neither read is sent. **Next step**: the reporter confirms the warnings are gone, or sends `viva-camctl xml` so the inference can be checked against the XML |
| TC-24 | Settle in-flight heartbeats (ADR-0023) against hardware | P2 | S | planned | **Waiting on hardware; partly answered.** [#164](https://github.com/VitalyVorobyev/viva-genicam/pull/164) sends READREG/READMEM(CCP) while a command is still outstanding, once an ACK wait outlasts the keepalive period; the facade turns these probes on whenever it holds control (`GigeRegisterIo::new`). They are fire-and-forget: a reply is drained and silence ends nothing (`recv_for_request`, `crates/viva-gige/src/gvcp.rs`). **Seen on hardware** ([#163](https://github.com/VitalyVorobyev/viva-genicam/issues/163#issuecomment-6118461248)): on a Micro-Epsilon scanCONTROL 8500-50 (`GevHeartbeatTimeout` 5000 ms) the reporter saw CCP reads sent during a `PENDING_ACK`ed command go unanswered — silence, not `BUSY` — and answered normally after the final ACK; and with no heartbeats, control held until 4 s after a 5 s pending command's final ACK and was lost by 6 s after it, so that firmware pauses or refreshes the lease while a command is pending (the reporter's capture cannot tell which). On that device the probes are harmless and unneeded. Open: (1) whether any device lets control expire during a pending command, which is what the probes are for; (2) the reporter also saw the first request right after a slow command go unanswered, a retry succeeding — whether that happens with no probes sent during the pending phase (a bare `GigeDevice` sends none). aravis sends nothing in between (`arvgvdevice.c:179–325`). **Next step**: the reporter's control-only captures |
| TC-27 | USB3 Vision has never met a camera | **P1** | S | blocked | **Milestone U; waiting on hardware.** The protocol was rebuilt to GenCP 1.2, the Grasshopper3's own XML (`PGR_GS3_U3_23S6M.xml`), aravis and Wireshark in 0.8; before that no layer matched them. What still rests on no hardware: (1) the SBRM's SIRM address, the SIRM layout and the stream leader/trailer come from aravis and Wireshark only — the USB3 Vision standard is not freely available; (2) the payload transfer arithmetic is aravis's, except that the transfer size is aligned down (`StreamLayout::new`); (3) aravis resets the stream endpoint before enabling it (`arv_uv_device_reset_stream_endpoint`) and we do not; (4) events (EIRM) are not implemented. **Next step**: ask the first USB3 Vision reporter for `viva-camctl report --usb 0`, which records the bootstrap registers raw |
| TC-33 | GenApi XML from other URL schemes; manifest and cache | P2 | M | planned | **Not planned for 0.9.0.** `crates/viva-genapi-xml/src/fetch.rs:110-126` reads only `Local:` URLs (zipped or not) and refuses named local, `http:` and `file:` URLs. No manifest table, SHA-1 check or host-side cache; the only override is building a `Camera` by hand from other XML |
| TC-34 | No FileAccess helper or firmware update | P2 | L | planned | **Not planned for 0.9.0.** `FileAccessBuffer` appears in 8 of 38 corpus documents, 2 with `<pLength>` (GA-09). The buffer is reachable through `get_register`/`set_register`, but nothing drives the file-access protocol (`FileSelector`, `FileOperationSelector`, `FileOperationExecute`), and there is no firmware update path |
| TC-35 | No PTP (IEEE 1588) helpers | P2 | M | planned | **Not planned for 0.9.0.** Nothing configures or reads PTP; `GevIEEE1588` appears in 6 corpus documents |
| TC-36 | JPEG, multi-part and GenDC payloads are counted, not assembled | P2 | M | planned | **Not planned for 0.9.0.** The receive engine assembles images (`0x0001`, `0x4001`) and chunk data (`0x0004`, `0x4004`); every other payload type — JPEG `0x0006`, multi-part `0x000A`, GenDC `0x000B` — is counted in `frames_unsupported` and not delivered (`Assembler::on_leader`, `crates/viva-genicam/src/stream/assembly.rs`). No reporter has needed one: the scanCONTROL on [#93](https://github.com/VitalyVorobyev/viva-genicam/pull/93) sends `0x4001`. Scheduled when a camera that needs one is reported |
| TC-38 | Telling a takeover from a refused register on a camera that does not name its controller | P2 | S | planned | **Waiting on hardware.** Control is marked lost on certain evidence only (`GigeDevice::ping_control_channel`): CCP read without control bits, or — where GVCP Capability bit `0x0800_0000` says the camera names its primary application at `0x0A04`/`0x0A14` — another application's IP and port there. Without that bit, CCP reads as controlled whoever holds it (aravis's fake and ours return its value to every reader), so a takeover after an expired heartbeat shows only as writes refused with `ACCESS_DENIED`, which a register may also answer for its own reasons; the session is then left `Held`. Pylon writes the heartbeat instead (aravis's comment, `arvgvdevice.c:470`). Open too: whether a device accepts writes while no application holds control, which both fakes allow. A capture of two applications on one camera settles both |
| TC-39 | Widened WRITEMEMs on hardware | P2 | S | planned | **Waiting on hardware.** A write shorter than a word, or off a word boundary, now reads the words around it and writes them whole (`GigeDevice::write_mem`), on the reading that GVCP carries whole aligned words, as READMEM does ([#35](https://github.com/VitalyVorobyev/viva-genicam/issues/35)). No device has been seen to reject an unaligned WRITEMEM; aravis pads one with whatever its buffer held. The one vendor register it applies to in the corpus is Sony CVC-EH6300's 1-byte `RegStatusOutputValueAll` (RW, `0xA078`); a read with side effects in the same word would be the risk. A `-vv` log of writing it settles it |
| TC-37 | Chunk and event layouts rest on no capture | P1 | S | blocked | **Waiting on hardware.** ADR-0026's layouts come from the vendor corpus, aravis (`arv_buffer_get_chunk_data`) and Wireshark (`dissect_extra_chunk_info`, `dissect_eventdata_cmd`); the GigE Vision text is not available. Unconfirmed on any camera: the backward scan with 32-bit big-endian tags, the image as the first chunk of a `0x4001` payload, the trailer's chunk payload length and layout ID, and event ports addressing the event from its header (every corpus timestamp is at 0x8, the scanCONTROL's at 0x10 with extended ids). Baumer HXG20's `ChunkImageLength` at `<Address>-4` is read as the last four bytes of its chunk on the strength of GenICam Standard v2.1.1 §2.8.16 alone. A frame whose chunks do not parse is delivered whole and logged once per stream. **Next step**: from the first reporter with chunk mode on, a capture of one frame (Wireshark) and the `Chunk*` values `Camera::chunk_features` reads |

## SR — Streaming reliability

| ID | Task | Priority | Size | Status | Notes |
|----|------|----------|------|--------|-------|
| SR-23 | Confirm the receive engine's block-id and packet heuristics on hardware | P2 | S | planned | **Waiting on hardware.** Derived from aravis and arithmetic, verified only on the fake ([ADR-0025](adrs/adr0025-gvsp-receive-engine.md)): a block id up to 100 behind the newest is late; a *leader* of block 1 from anything but its predecessor is a restart; a data packet longer than the stride is refused, not written; the newest block does not time out while only its leader has arrived; the 100 ms inactivity default. A capture of one camera through an AcquisitionStop/Start, and of one whose packet size the host misjudges, settles them |
| SR-24 | Do cameras accept `PACKETRESEND_CMD` from the stream socket? | P1 | S | planned | **Waiting on hardware.** The receive engine sends resend requests from the stream's own socket to the camera's GVCP port, as aravis does (`_send_packet_request`); the controlling application's GVCP traffic comes from another port. The GigE Vision specification is not available to us, so what it says about the request's source is not quoted here. A camera that answered only the control channel's port would ignore every request: `resend_requested` climbing with `resend_recovered` at 0 on a lossy link. **Next step**: from a reporter whose stream loses packets, `viva-camctl stream -vv` output (it logs each request) and, ideally, a capture of one request and what follows |
| SR-26 | The Zenoh frame header carries no row stride | P2 | S | planned | `viva_zenoh_api::FrameHeader` (16 bytes) has width, height and format but not the leader's `padding_x`, so `viva-service` publishes a padded frame and Studio's remote mode draws every row after the first shifted (`studio/crates/viva_streamer/src/zenoh_source.rs` passes no stride). Embedded mode passes `Frame::row_stride`. A header version bump, or the service stripping the padding before it publishes |
| SR-25 | How does a camera answer a resend it cannot serve? | P2 | S | planned | **Waiting on hardware.** Only the fake has answered. The engine reads a bare GVSP header with status `0x800C`/`0x8012` (close that range), `0x8011` (also stop earlier ones) or `0x8010`/`0x8014` (keep retrying), in any packet format, matched to a range by its packet id; status names from Wireshark. Open: (1) whether cameras send these or stay silent, and one per packet or per range; (2) whether resent packets carry status `0x0100`; (3) the standard-id request's first word — Wireshark reads `[channel u16][block u16]`, aravis writes the block id across the whole word, so they agree only on channel 0. A capture of one camera answering a request for an old block settles (1) and (2) |

## DC — Device classes beyond area-scan

A laser profile scanner (Micro-Epsilon scanCONTROL 850050, [#93](https://github.com/VitalyVorobyev/viva-genicam/pull/93)) is in the corpus and `viva-pfnc` has its `Coord3D_*` codes, but nothing above `viva-pfnc` knows what a `Coord3D_*` frame is. Rows are scheduled only when verified against code or a wire capture, never against our idea of what a 3D camera sends.

| ID | Task | Priority | Size | Status | Notes |
|----|------|----------|------|--------|-------|
| DC-02 | The Zenoh wire format carries no `Coord3D_*` variants | P2 | M | planned | **Waiting on hardware.** `viva_zenoh_api::PixelFormat` has one 3D entry, `Coord3D_C16`, which the scanCONTROL does not advertise, and none of the four it does. `#[serde(other)] Unknown` swallows them, so `publish_image_meta` (`crates/viva-service/src/acquisition.rs`) announces `payload_size` as `w * h * 1`. Adding variants changes the one-byte map in `pixel_format_to_u8` (`crates/viva-zenoh-api/src/frame_header.rs`) — a wire-format change; land it with DC-03 |
| DC-03 | No `Scan3d*` SFNC constants, so a `Coord3D` payload cannot be interpreted | P2 | M | planned | **Waiting on hardware.** `viva-sfnc` has no `Scan3d*` constants and no Rust source reads `Scan3d`, so a `Coord3D_AC16` buffer is raw integers with no metric meaning or invalid-point mask. `MicroEpsilon_scanCONTROL_850050.xml:6104+` declares `Scan3dCoordinateScale`/`Offset`/`Selector`, `Scan3dInvalidDataFlag`/`Value` and `Scan3dOutputMode`, applying scale and offset only to `Coord3D_AC16` (`:6188`, `:6218`); `DeviceScanType` (`:40-61`) offers `Areascan3D`/`Linescan3D`. On the wire `Scan3dInvalidDataValue` is LE `f32` `ff ff ff 7e` = `1.7014117e38`, matching the node ([#93 capture](https://github.com/VitalyVorobyev/viva-genicam/pull/93#issuecomment-5162882332)). The nodes already parse as `Float`/`Enumeration`; add constants and a reader |
| DC-04 | No fake can emit a `Coord3D_*` frame | P2 | M | planned | **Waiting on hardware.** `viva-fake-gige` can send payload type `0x4001` and sizes images by PFNC bit depth, but `viva-fake-u3v`'s `bytes_per_pixel` knows only RGB8 = 3, else 1, so DC-02/DC-03 have no end-to-end test. **Wire facts** (scanCONTROL 850050, [#93 capture](https://github.com/VitalyVorobyev/viva-genicam/pull/93#issuecomment-5162882332)): leader payload type `0x4001` (image + extended chunk; not GenDC, not multipart), PFNC `0x026000C0`; coordinates little-endian, interleaved per point, 4 / 4 / 8 / 12 bytes for `Coord3D_C32f` / `_AC16` / `_AC32f` / `_ABC32f` (matching `viva_pfnc::PixelFormat::bytes_per_pixel`); in the four decoded `(A, B, C)` tuples `B` is zero for a single profile. **Next step**: build the fake from that capture; P2 behind GA-09 |
| DC-05 | Event-vision blocks: a Python `next_block` | P2 | S | planned | **Waiting on hardware.** From [#138](https://github.com/VitalyVorobyev/viva-genicam/issues/138) / [#139](https://github.com/VitalyVorobyev/viva-genicam/pull/139) (Lucid Triton2 EVS, Sony IMX636); the service already publishes event blocks on `genicam/devices/{id}/evs`. Remaining: (1) `viva-pygenicam` exposes only `next_frame`, so Python receives an event block as a 1 × N frame; (2) only the fake has delivered an event block through the receive engine |
| DC-06 | `viva-camctl stream --raw-out` edge cases | P2 | S | planned | **Waiting on hardware.** From reviewing [#154](https://github.com/VitalyVorobyev/viva-genicam/pull/154). (1) The file is opened with `append(true)` (`crates/viva-camctl/src/cmd_stream.rs`), so reruns concatenate captures, even of different EVT formats; truncate by default with an explicit `--append`, or refuse a format change. (2) `--save` defaults to 1 (`crates/viva-camctl/src/cli.rs`), so `--raw-out` still writes a `block_0001.*`. (3) The file is created before the first block, so an image stream leaves an empty file |
