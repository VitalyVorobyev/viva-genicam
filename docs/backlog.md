# Backlog

Immediate, actionable tasks. Mid-term direction lives in
[roadmap.md](roadmap.md); shipped work is recorded in
[CHANGELOG.md](../CHANGELOG.md).

**Legend**

- Priority: **P0** (do next) / **P1** (soon) / **P2** (when convenient)
- Size: **S** (hours) / **M** (a day or two) / **L** (several days) /
  **XL** (a week+)
- Status: `planned` / `in-progress` / `blocked`

Every row carries its evidence — a corpus count, a `file:line`, or an issue
number — so priority can be argued from data rather than from intuition
([ADR-0018](adrs/adr0018-genapi-conformance-over-convenience.md)).

**This file only lists open work.** A row is deleted when it ships; the record
of what shipped, and why, is [CHANGELOG.md](../CHANGELOG.md). It used to keep
its completed rows, and at 69 of them the working list was 131 KB of mostly
history.

Two rules that came out of rows deleted this way, kept because they are about
how to file a row rather than about any one defect:

- **Do not propose downgrading a log level before the warning's cause is
  known** — that is a proposal to delete the evidence. A row once read a
  per-frame `WARN chunk header truncated remaining=6` as cosmetic and guessed
  the fake was appending bytes it should not. The fake was emitting a
  spec-conforming trailer and the parser was reading it at the wrong offset;
  the warning was the only outward sign of a defect that silently broke chunk
  decoding on every real camera.
- **A row filed from fake-camera output alone is a hypothesis.** That one only
  became obvious when a real JAI emitted the identical `remaining=6`, which is
  what showed the fake was not the variable.

| TC-05 | Accept the payload types cameras actually send | P1 | M | planned | **This entry's own premise was wrong and is corrected here.** It claimed Image Extended Chunk (0x4001) "never opens a frame". It does open one: `parse_leader` compares `cursor.get_u16() as u8` against `PAYLOAD_TYPE_IMAGE` (`crates/viva-gige/src/gvsp.rs:266`), and `0x4001 as u8 == 0x01`, so the truncating cast lets it through — and then stores `payload_type: 0x01`, discarding the fact that the block carries chunks. So the defect is not rejection but *silent misclassification*, which is why #70's JAI streamed at all. What is genuinely rejected is any payload type whose **low byte** is not 0x01 (0x0002 raw data, 0x0004 file), and packet format 0x04 (single-packet block, `gvsp.rs:235-240`). Separately `parse_packet:233` derives a header-level payload type from `payload[0..2] >> 4` — those two bytes are the GVSP **status** word, not a payload type — and passes it to `parse_leader` as `_payload_type_header`, which discards it. | TC-16 | One flat `StatusCode` cannot serve both GVCP and GenCP | P0 | M | in-progress | The tables share `0x0000`, `0x8001`-`0x8007` and `0x8FFF`, then **conflict at the same code**: `0x800B` is `NO_MSG` (deprecated) in GVCP but `MSG_TIMEOUT` in GenCP. GVCP additionally owns the packet-resend family (`0x0100`, `0x800C`-`0x8017`); GenCP owns `0xA001`-`0xA101`. So adding entries cannot make the shared enum correct — it needs a shared core plus per-transport extension. **Write an ADR.** This also corrects the `PENDING_ACK` rationale we recorded for U3V, and that half is worse than "unrecognised" — it is **silent wrong data**. `decode_ack` reads the acknowledgement's command id into `let _opcode` and discards it (`viva-u3v/src/control.rs:267`), and `transact` validates only `request_id` (`:180`). A GenCP pending-ack is a distinct command (`0x0805`) carrying `time_to_completion` in its SCD, with a *success* status — so on a device that uses one we accept it as the real answer and **return the timeout bytes as the register value**. A 4-byte `ReadRegister` gets a plausible-looking wrong number. Meanwhile `StatusCode::Unknown(0x8006)` (`:29`, `:189`) only ever fires on a genuine `ACCESS_DENIED`, which we then sleep-and-retry 100× (`MAX_PENDING_RETRIES`) before reporting `Timeout` instead of "access denied". Both halves wrong, mutually reinforcing. aravis gets this right and shows the shape of the fix (`arvuvdevice.c:344-373`): read status *and* command id, test `command == PENDING_ACK` first and independent of status, then require `command == expected_ack_command` before accepting the payload — we already have `OpCode::ack_code()` for that comparison. The test at `control.rs:472` asserts the misreading back to us: fourth occurrence of the pattern where the fake asserts our own misreading back to us ([ADR-0019](adrs/adr0019-transport-conformance-and-spec-derived-fakes.md)). The `StatusCode::from_raw` table was corrected in 0.4.0, which already made the `Unknown(0x8006)` arm dead code. **Done so far:** pending-ack is keyed off command id `0x0805` (`viva_gencp::PENDING_ACK_COMMAND`), `decode_ack` keeps the command id, `transact` requires it to equal `OpCode::ack_code()` before accepting a payload, and the SCD timeout is read as a little-endian `u16` at offset 2 — the old big-endian `u32` read turned a 1 000 ms request into 59 395 ms. `build_ack` now takes an explicit command id, deleting the "opcode doesn't matter for most tests" comment that was the assumption behind the whole defect. **Remaining:** the per-transport wrapper types (ADR-0020 points 1-2). | TC-18 | Stale-ack absorption is bounded by a count, not a deadline | P2 | S | planned | Noted while merging [#91](https://github.com/VitalyVorobyev/viva-genicam/pull/91), and promised to its author. That PR correctly stopped a mismatched acknowledgement from triggering a resend — a retransmission with a fresh request id is indistinguishable from a new command, which is how a non-idempotent `WRITEMEM` gets executed twice — and now absorbs unrelated datagrams while waiting. But it bounds the absorption by a *count* (`mismatched_acks < MAX_RETRIES`) and each `recv_absorbing_pending` call restarts a full `CONTROL_TIMEOUT`, so a device trickling stale acks can stretch one attempt to `4 × 500 ms` rather than capping at a single 500 ms window. aravis bounds the same window by wall clock instead (`arvgvdevice.c`, `timeout_stop_ms` recomputed only on PENDING_ACK). Bounded either way and strictly better than resending, so this is a latency shape to revisit if it appears on hardware, not a defect. **Negative data point 2026-08-03** ([#93 comment](https://github.com/VitalyVorobyev/viva-genicam/pull/93#issuecomment-5162882332)): #91's own author stress-tested a scanCONTROL 850050 on firmware 3.0.0 and saw no slow control transactions, stale acknowledgements or retries — ROI and line-rate changes were accepted during a live stream without timeouts. One device is not a clearance, but nothing has pushed this above P2 |
| TC-21 | `BAD_ALIGNMENT` on a real camera's event registers | **P1** | M | planned | **Seen on hardware** ([#112](https://github.com/VitalyVorobyev/viva-genicam/issues/112), attached Studio log): **62** reads of `pEventStream*Reg` on a Vieworks FS3200T return `device reported status BAD_ALIGNMENT (0x8005)`. We have been here — the Hikrobot in [#35](https://github.com/VitalyVorobyev/viva-genicam/issues/35) rejected unaligned READMEM counts, and `read_mem` now rounds the *count* up to a multiple of four (`crates/viva-gige/src/gvcp.rs:1103-1120`). This is the other half: the *address*. Nothing rounds or checks it, and a `<Register>`/`<IntReg>` whose `<Address>` is not 4-byte aligned goes to the wire as-is. Confirm against the camera's XML before assuming — ask the reporter for it, per the corpus rule, since that also settles whether these are `<IntReg>` at an odd address or something else entirely. Note the status code only reads correctly at all because the `StatusCode::from_raw` table was corrected in 0.4.0; before 0.4.0 this would have printed `device busy`. **READREG dispatch does not fix this**, and should not claim to: only an aligned 4-byte access goes out as READREG (`single_register_address`, `crates/viva-gige/src/gvcp.rs`), so an unaligned address stays a READMEM at that address, and covering an 8-byte event register would need multi-register batching, which was deliberately left out because a multi-register READREG has no defined atomicity. ## DC — Device classes beyond area-scan

A laser profile scanner joined the corpus on 2026-07-31 (Micro-Epsilon
scanCONTROL 850050, contributed alongside
[#93](https://github.com/VitalyVorobyev/viva-genicam/pull/93)), and #93 added
the six PFNC codes it needs. **Adding the format codes is not the same as
supporting the device class.** Nothing above `viva-pfnc` knows what a
`Coord3D_*` frame is; these rows are what that costs, each measured against
that document or against the code rather than against the idea of a 3D camera.

Only the frame-sizing half has been fixed (0.4.0). The rest are filed rather than built because
nobody has reported *streaming* one of these devices through this stack, and
the evidence hierarchy puts a hardware report above our inference — DC-04 in
particular would have us guess what the wire looks like, which is the ADR-0019
failure of fake and client agreeing only with each other.

| ID | Task | Priority | Size | Status | Notes |
|----|------|----------|------|--------|-------|
| DC-02 | The Zenoh wire format carries no `Coord3D_*` variants | P2 | M | planned | `viva_zenoh_api::PixelFormat` (`crates/viva-zenoh-api/src/lib.rs:358-388`) has exactly one 3D entry, `Coord3D_C16` — which the scanCONTROL does not advertise — and none of the four it does. `#[serde(other)] Unknown` means `ImageMeta.pixel_format` decodes any of them to `Unknown` without complaint, so `payload_size` is announced as `w * h * 1` (`crates/viva-service/src/acquisition.rs:419-428`). Extending it changes the one-byte discriminant map (`crates/viva-zenoh-api/src/frame_header.rs:108-138`, populated to 26), so it is a wire-format change rather than a local fix, and it should land with DC-03 so the published values mean something |
| DC-03 | No `Scan3d*` SFNC constants, so a `Coord3D` payload cannot be interpreted | P2 | M | planned | `crates/viva-sfnc/src/lib.rs` defines exactly one constant, `CHUNK_MODE_ACTIVE`; `Scan3d` appears in no source file in either workspace. `MicroEpsilon_scanCONTROL_850050.xml:6104+` carries the full block — `Scan3dCoordinateScale`, `Scan3dCoordinateOffset`, `Scan3dInvalidDataFlag`, `Scan3dInvalidDataValue`, `Scan3dOutputMode`, `Scan3dCoordinateSelector` — and the document itself states at `:6188` and `:6218` that scale and offset apply only when `PixelFormat` is `Coord3D_AC16`. Deliberately P2 — do this once a reporter tells us what a scanCONTROL actually puts in its GVSP leader, because a fake built on our guess would confirm the guess. **That condition was met on 2026-08-03** ([#93 comment](https://github.com/VitalyVorobyev/viva-genicam/pull/93#issuecomment-5162882332)). | DC-05 | An event-vision block is published on the image topic as a 1×64000 image | P1 | M | planned | From [#138](https://github.com/VitalyVorobyev/viva-genicam/issues/138) / [#139](https://github.com/VitalyVorobyev/viva-genicam/pull/139) (Lucid Triton2 EVS, Sony IMX636). `crates/viva-service/src/acquisition.rs` calls `next_frame()`, so an event block arrives as a `Frame` with `width = 1`, `height = 64000` and an unnamed PFNC code; the accompanying `expected_payload_len → None` stops it being dropped as undersized, so it is published rather than discarded — with a `FrameHeader` describing something that is not an image and `PixelFormat::Unknown`.
